# 대화 기록 저장 방식 분석

## 현재 구현 방식
- **저장 위치**: PostgreSQL `scenario_progress.conversation` (JSON 컬럼)
- **저장 시점**: 시나리오 종료 시 (`end_scenario`)
- **데이터 형식**: JSON 배열
  ```json
  [
    {
      "role": "user",
      "content": "안녕하세요",
      "created_at": "2025-01-15"
    },
    {
      "role": "assistant",
      "content": "안녕하세요! 반갑습니다.",
      "created_at": "2025-01-15"
    }
  ]
  ```

---

## 장점 ✅

### 1. **트랜잭션 일관성**
- 시나리오 종료와 대화 저장이 하나의 트랜잭션으로 처리
- 데이터 일관성 보장

### 2. **간단한 조회**
- JOIN 없이 바로 조회 가능
- `progress_id`로 바로 접근

### 3. **백업/복구 용이**
- DB 백업에 자동 포함
- 데이터 손실 위험 낮음

### 4. **PostgreSQL JSON 성능**
- PostgreSQL의 JSON 타입은 잘 최적화됨
- 인덱싱 가능 (GIN 인덱스)

---

## 단점 ⚠️

### 1. **DB 용량 증가**
- 대화가 많아지면 DB 용량 급증
- 예상: 시나리오당 평균 10턴 × 100자 = 약 1KB
  - 사용자 1000명 × 시나리오 10개 = 약 10MB
  - 사용자 10,000명 × 시나리오 50개 = 약 500MB

### 2. **성능 이슈 가능성**
- JSON 필드가 매우 커지면 쿼리 성능 저하
- PostgreSQL JSON은 TEXT 기반이라 큰 데이터는 느림

### 3. **백업 시간 증가**
- DB 백업 시간이 길어질 수 있음

### 4. **확장성 제한**
- 대화가 매우 긴 경우 (수백 턴) 문제 가능

---

## 대안 비교

### 옵션 1: 현재 방식 유지 (DB JSON) ⭐ **권장 (현재 규모)**
**적합한 경우:**
- 사용자 수가 수천 명 이하
- 시나리오당 평균 턴 수가 50턴 이하
- 간단한 구현 유지 원함

**장점:**
- 구현이 이미 완료됨
- 추가 작업 불필요
- 조회가 간단함

**단점:**
- 대규모 확장 시 문제 가능

---

### 옵션 2: 별도 테이블로 분리
```sql
CREATE TABLE conversation_messages (
    message_id SERIAL PRIMARY KEY,
    progress_id INTEGER REFERENCES scenario_progress(progress_id),
    role VARCHAR(20),
    content TEXT,
    created_at DATE,
    message_order INTEGER
);
```

**장점:**
- 정규화된 구조
- 개별 메시지 조회/수정 가능
- 인덱싱 최적화 가능

**단점:**
- JOIN 필요 (성능 오버헤드)
- 구현 복잡도 증가
- 마이그레이션 필요

---

### 옵션 3: 파일 시스템 저장
```
uploads/conversations/
  └── {progress_id}.json
```

**장점:**
- DB 부하 감소
- 파일 단위 관리 용이
- 확장성 좋음

**단점:**
- 트랜잭션 일관성 보장 어려움
- 백업 복잡도 증가
- 파일 시스템 의존성

---

### 옵션 4: S3/객체 스토리지
**장점:**
- 무한 확장성
- 비용 효율적 (저장만)
- CDN 연동 가능

**단점:**
- 외부 서비스 의존성
- 추가 비용
- 구현 복잡도 증가

---

### 옵션 5: 하이브리드 (DB + 파일)
- **메타데이터**: DB에 저장 (시나리오 정보, 요약 등)
- **전체 대화**: 파일 시스템에 저장

**장점:**
- 각 방식의 장점 활용
- 확장성과 조회 성능 균형

**단점:**
- 구현 복잡도 높음
- 두 저장소 동기화 필요

---

## 권장 사항

### 현재 단계 (초기/중소 규모)
✅ **현재 방식 유지 (DB JSON)**
- 사용자 수가 수천 명 이하
- 시나리오당 평균 턴 수가 적당함
- 구현이 이미 완료되어 있음

**최적화 방법:**
1. JSON 필드에 GIN 인덱스 추가 (필요시)
2. 오래된 대화 기록 아카이빙 (선택적)
3. 대화 길이 제한 설정 (예: 최대 100턴)

### 성장 단계 (수만 명 이상)
🔄 **옵션 2 (별도 테이블) 또는 옵션 5 (하이브리드) 고려**
- 사용자 수가 수만 명 이상
- 대화 기록이 매우 많아짐
- 성능 이슈 발생 시

---

## 최적화 제안 (현재 방식 유지 시)

### 1. 인덱스 추가 (필요시)
```sql
CREATE INDEX idx_scenario_progress_conversation 
ON scenario_progress USING GIN (conversation);
```

### 2. 대화 길이 제한
```python
# 최대 100턴까지만 저장
MAX_CONVERSATION_TURNS = 100
if len(conversation_list) > MAX_CONVERSATION_TURNS:
    conversation_list = conversation_list[-MAX_CONVERSATION_TURNS:]
```

### 3. 오래된 데이터 아카이빙
- 1년 이상 된 대화 기록은 별도 아카이브 테이블로 이동
- 또는 파일로 내보내기

### 4. 압축 고려
- 대화 내용이 매우 길 경우 압축 저장 (선택적)

---

## 결론

**현재는 DB JSON 방식 유지 권장**
- 구현이 완료되어 있고
- 초기/중소 규모에서는 문제없으며
- 필요 시 나중에 마이그레이션 가능

**모니터링 지표:**
- DB 용량 증가율
- 쿼리 성능 (대화 조회 시간)
- 사용자 수 증가율

**마이그레이션 시점:**
- DB 용량이 1GB 이상
- 대화 조회 쿼리가 1초 이상
- 사용자 수가 10,000명 이상
